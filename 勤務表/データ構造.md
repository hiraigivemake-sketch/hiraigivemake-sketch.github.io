# 勤務表 データ構造 v2

②訪問スタッフの勤務表作成アプリ。単一HTML（`勤務表.html`）にデータ層・セルフテスト・画面を内蔵する。①訪問スケジュールと同じ作り（localStorage の1キーにJSON、マスタは無効化で運用、保存前に全体検証）。

## 方針

- 保存先は `localStorage` の `kinmu_hyo_db`。①とはキーが別で、同じブラウザでも互いに干渉しない。
- 1日1人1種別。勤務表のセルは（スタッフ, 日付）で一意。
- 月に「作成中／確定」と「希望の締切」の状態を持つ。確定月は勤務表を変更できず、締切後は希望を変更できない。
- 制約の重さは `RULE_LEVEL`（`block`=保存不可・自動作成が避ける / `warn`=注意）で一元管理し、画面はこれに従う。
- サンプルは架空名のみ。①のサンプルとスタッフIDを揃えてあり、書き出した勤務データを①でそのまま取り込める。

## ShiftType（シフト種別）

`{ id, code（1〜2文字）, name, start, end, breakMin, isWork, usesPto, availableForVisits, color, order, archived }`。実働時間は `(終了 − 開始 − 休憩)`。`isWork=false` は休み（時刻なし）。`usesPto` は有給残を消費する休み。`availableForVisits=false` の勤務（研修など）は①へは「休み」として渡す。スタッフの既定シフトに使われている種別は無効化できない。

## Staff（スタッフ）

`{ id, name, displayName, role, employment, weeklyHours（週所定）, workDows（勤務できる曜日）, defaultShiftTypeId, canOncall, isManager, ptoBalance（有給残日数）, employmentPeriod, color, archived, note }`。

## Wish（希望）

`{ id, staffId, date, kind, shiftTypeId, strength, note }`。`kind` は `off` 休み / `pto` 有給 / `work` 出勤 / `shift` シフト指定 / `noOncall` オンコール不可。`strength` は `must`（自動作成が必ず守り、違反はブロック）/ `prefer`（警告）。（スタッフ, 日付）で一意。

## ルール

| code | 重さ | 内容 |
|---|---|---|
| `staffNotEmployed` | block | 在籍期間外 |
| `oncallNotAllowed` | block | オンコール不可の人にオンコール |
| `ptoExceeded` | block | その月の有給日数が有給残を超える |
| `consecutiveDays` | block | 連続勤務が上限を超える（前後の月もまたいで数える） |
| `mustWishViolated` | block | 必須希望に反する |
| `belowMinNurses` / `belowMinTotal` / `oncallMissing` | block | 日の配置不足（営業日・休業日で基準を切替） |
| `noRestInWeek` | warn | 暦週（日〜土）が全日埋まっていて休みがない |
| `weeklyHoursOver` | warn | 暦週の勤務時間が上限超過 |
| `preferWishViolated` / `outsideWorkDows` / `oncallOnOff` / `oncallConsecutive` / `oncallExtra` | warn | 希望違反・勤務曜日外・営業日に休みのままオンコール（休業日のオンコールは通常運用なので対象外）・連日のオンコール・オンコール過多 |
| `hoursGap` | warn | 勤務時間＋有給（1日あたり所定で換算）が所定時間と1日分より大きくずれる。所定時間 = 1日あたり所定（週所定 ÷ 勤務曜日数）× その月の勤務曜日のうち休業日でなく在籍している日数 |
| `unfairOncall` / `unfairClosedWork` | warn | オンコール回数、週末・休業日出勤の最多と最少の差が2を超える |
| `nurseFteLow` | warn | 看護職員の常勤換算が 2.5 未満 |
| `unassigned` | warn | 未入力のセル |

`rules.checkEntry(db, entry)` がセル単位、`checkDay(db, date)` が日単位、`checkMonth(db, ym)` が月全体（公平性・常勤換算を含む）を返す。

## 自動作成 `rules.autoFill(db, ym, { overwrite })`

1. 必須の休み・有給・シフト指定・出勤希望を先に置く。
2. 日ごとに、看護職員→全体の順で最低人数を満たすまで出勤を割り当てる。候補は在籍中・勤務曜日・連続上限内・休み希望なしの人で、所定時間に対する不足が大きい人と出勤希望の人を優先。営業日は所定時間に満たない人も出勤にする。
3. 残りは公休。週に休みがない人は、配置に余裕のある日を公休に戻す。
4. オンコールを毎日、担当可能で連日にならず回数の少ない人へ（出勤している人を優先）。

方針 `strategy` は `balanced`（所定時間の不足が大きい人から）/ `wishes`（シフト指定の希望も使う）/ `fair`（休業日の出勤とオンコールを回数の少ない人から）。`rules.generateCandidates(db, ym)` は3方針を複製データで作って `scoreMonth`（要対応・注意・希望違反・オンコール回数の差・週末出勤の差・所定との差・未入力・看護の常勤換算）とともに返し、`applyCandidate` で選んだ案に置き換える。元のデータは比較中は変わらない。

`overwrite=false` は空欄だけを埋める（手で入れたセルは触らない）。人手が足りない日は `unmet` で返し、画面は件数と例を知らせる。1回の走査で必ず終わる。`rules.copyPattern(db, fromYm, toYm)` は前月のスタッフ×曜日で最も多かった種別を空欄に写す（オンコールは写さない）。

## 書き出し・取り込み

- `exporters.shiftsCsv / shiftsJson(db, ym)`: ①訪問スケジュールの「スタッフ › 取り込む」が読む形式（日付, スタッフ, staffId, 開始, 終了, 区分）。勤務は時刻、休みと研修は「休み」。
- `exporters.rosterCsv(db, ym, mode)`: 給与・集計用。スタッフ×日の略号（オンコールは ◎）と月集計。`mode` が `actual` なら実績（`actualShiftTypeId`、未入力は予定どおり）で集計し、予定と異なる日数の列を加える。
- 実績: `roster[].actualShiftTypeId` に実際の種別を入れる（`repo.roster.setActual`。確定月でも可）。`derive.effectiveTypeId(entry, mode)` で予定／実績を切り替え、`staffMonthStats` / `dayStats` / `fte` は `mode` 引数で実績集計になる。`derive.actualChanges(db, ym)` が差異一覧。
- 希望の提出（サーバーなし）: `exporters.wishPacket(db, ym)` が本人に渡す提出用セット（スタッフ・シフト種別・対象月の希望と休日。勤務表は含まない）。本人の端末では `importers.loadWishPacket` で提出モードのデータとして読み込み（希望とデータのタブだけが使える）、自分を選んで希望を入れ、`exporters.wishSubmission(db, ym, staffId)` の提出コード（JSON）をファイルかコピーで管理者へ送る。管理者は `importers.parseWishSubmission` → `repo.wishes.applySubmission` で取り込む。その人のその月の希望を置き換え、IDが一致しなければ氏名で照合し、締切後や対象月外の日付は拒否する。
- `importers.staffFromVisitApp(json)`: ①のデータ書き出しJSONからスタッフを取り込む。勤務可能枠から週所定時間と勤務曜日を推定し、6.5時間以下なら既定シフトを時短にする。同じIDは飛ばす。

## 画面

| タブ | 内容 |
|---|---|
| 勤務表 | 「予定／実績」を切り替えられる。実績モードではセルをクリックして実際に勤務した種別と、オンコール待機の有無・呼び出し回数を入れる（確定月でも可、未入力は予定どおり）。予定モードの「案を比較」で3方針の案を点数付きで並べて適用できる。予定と異なる日は点線で囲み「実」印を付ける。予定モードはスタッフ×日のグリッド。セルをクリックして種別・オンコール・備考・クリア。希望は左上に小さく表示（赤は必須）。制約違反は右下の点（赤=要対応、黄=注意）。下段に出勤・看護・オンコールの人数（不足は赤）。右端に月集計。自動作成／やり直す／前月の型をコピー／月次チェック／確定 |
| 希望 | 同じグリッドで休み・有給・出勤・シフト指定・オンコール不可を入力。必須の切替、スタッフで絞り込み、希望の締切。「提出用セットを書き出す」「提出を取り込む」（貼り付けまたはファイル）、スタッフを選ぶと「希望を提出する」 |
| 集計 | 予定／実績を切り替えられ、実績モードでは呼び出し回数と手当額、予定と実績の差異一覧（種別と待機）も表示。看護職員と全体の常勤換算、月次チェックの件数、スタッフごとの出勤・休・有給・オンコール・週末出勤・勤務時間・所定・差・未入力 |
| 出力 | 勤務表（A4横の印刷）、個人別、給与・集計用CSV（予定／実績を選択。実績は有給込み時間と予定と異なる日数の列を含む）、①向け勤務データ（CSV/JSON） |
| マスタ | スタッフ、シフト種別、休日（祝日一括登録）、設定（配置基準・労務上限・オンコール手当） |
| データ | サンプル、JSONの書き出し・読み込み、①JSONからスタッフ取り込み、希望の提出用セットの読み込み（本人の端末）、セルフテスト |

## 今後の候補

当初の候補はすべて実装済み。運用して見えた要望に応じて次を検討する。

1. 提出用セットと提出コードの受け渡しを自動化する共有先（共有フォルダやチャットの連携）。
2. 複数案の方針を設定で調整できるようにする（公平性の目標値、優先するスタッフ）。
3. 手当の種類を増やす（休日出勤・時間外）と、給与ソフトの取り込み形式への合わせ込み。
